第 2 章 · 蓝鲸 DBM 中的集群形态

平台支持两类 MongoDB 集群类型，对应 ClusterType 中的两个常量。本章帮助你 把 UI 字段、代码常量和真实拓扑对应起来，便于在控制台一眼看懂角色分布。

2.1类型一：MongoReplicaSet（副本集集群）类型

典型副本集拓扑：1 主 + 2 从（PSS），由复制协议自动选主；其中至少一个从节点担任 backup 节点，权重 0、不可被选为 Primary，专用于跑日常备份。

P mongod (Primary) 读写主 · priority≥1
▲ oplog 复制 / 选举心跳 ▼
S mongod (Secondary) 普通从 · 可被选主 · 可承接读
B mongod (Backup) priority=0 · hidden · 跑备份
🛡
部署原则（蓝鲸 DBM 默认规范）

除单节点测试场景外，生产副本集至少部署 3 个节点：1 个 Primary + 2 个 Secondary，确保高可用与数据冗余；2 个从节点中至少 1 个为 backup 节点，priority=0 永不当选 Primary，承担日常备份职责，避免备份对线上读写造成抖动。

节点角色矩阵

Primary 读写主

  • 唯一可接收写请求的节点
  • 产生 oplog，供从节点回放
  • 故障时由复制协议自动选主
priority ≥ 1votes = 1

Secondary 普通从

  • 持续从 Primary 拉取 oplog 回放
  • 可被选举为新的 Primary
  • 可承接 readPreference=secondary 读流量
priority ≥ 1votes = 1hidden = false

Backup 备份从

  • priority = 0：永不当选 Primary
  • hidden = true：客户端不可见，不分担线上读
  • 专用于 mongodump / 物理备份，避免影响业务
priority = 0votes = 1hidden = true
  • 常量：MongoReplicaSet
  • 访问入口：通常以 主域名 / cluster_entry 暴露；连接串可包含 replicaSet 参数。
  • 适用：数据量与写入可在单集群「多副本」满足时优先选用。
  • 容灾：3 节点架构允许任意 1 节点宕机仍可正常读写；如需更高可用性可扩展至 5/7 节点（奇数）。
⚠
为什么 backup 节点要 priority=0？

备份过程会消耗大量磁盘 IO 与 CPU。如果 backup 节点保留选主资格，一旦 Primary 故障被选为新主，正在执行的备份任务会与突增的线上流量竞争资源，导致业务抖动。priority=0 从制度上杜绝了这一风险。

蓝鲸 DBM 在元数据层为副本集每个成员定义了固定的角色名（instance_role）与子域名前缀，二者一一对应。代码常量见 backend/db_meta/enums/instance_role.py 中的 InstanceRole 与 backend/flow/consts.py 中的 MongoDBDomainPrefix。

backup MONGO_BACKUP backup.<set>.<app>.db Backup 从，priority=0 / hidden=true，专跑日常备份
📌
命名约束
  • 当前 DBM 每个副本集最多支持 11 个成员：m1 + m2~m10 + backup，对应 calculate_cluster.py 中 domain_prefix 的 11 个槽位。
  • 子域名前缀和角色名严格一一对应，不可自定义；例如不能把 m3 写成 m_3 或 node3。
  • 分片集群的 shard 内部同样沿用这套命名（每个 shard 是一个独立副本集）；config server 副本集成员同样用 m1/m2/m3/backup。
  • 分片集群的接入层 mongos 不属于副本集成员，使用独立子域名 mongos.<cluster>.<app>.db。

2.3按节点数量分类的部署形态 数量

同一套命名规则下，副本集会根据节点数量呈现三类形态。生产场景必须选用 3 节点及以上方案。

1

单节点（Standalone）

仅测试 / POC 场景

仅 1 个 mongod 实例，没有高可用、没有数据冗余。DBM 中通过集群标签 single_node:true 标识，巡检会跳过成员数检查。

m1 (Primary)
  • 计费用最低，但宕机即整集群不可用
  • 禁止承载生产业务，不跑日常备份
  • 典型用途：开发联调、临时压测环境
无 backup 节点 不可生产
3

三节点 PSS（推荐）

生产标准最小部署

蓝鲸 DBM 默认且推荐的副本集形态：1 Primary + 1 Secondary + 1 Backup，允许 1 节点宕机仍可读写。

m1 m2 backup
  • 选举仲裁需要奇数票，3 节点天然满足
  • backup 节点 priority=0 / hidden=true，不抢主、不承接业务读
  • 巡检要求：set 至少 3 个成员（check_affinity 中 min_members=3）
高可用 日常备份 性价比最佳
N

多节点（5/7/…，最大 11）

读扩展 / 跨城多副本

在 3 节点基础上扩容至 5 / 7 / 9 / 11 个成员（建议奇数），增加只读副本承接读流量或满足跨城容灾。

m1 m2 m3 m4 … backup
  • 新增成员依次占用 m4 → m10 槽位；backup 始终保留 1 个
  • 票数过多会增加选举开销，非必要不建议超过 7 节点
  • 跨城副本可设 priority=0 + hidden=true 仅作灾备从
读扩展 跨城容灾 上限 11
⚠
蓝鲸 DBM 的硬性约束
  • 副本集成员数最多 11 个（m1~m10 + backup），由代码 domain_prefix 数组写死。
  • 除带 single_node:true 标签的测试集群外，每个副本集 / shard 必须 ≥ 3 个成员，且至少包含 1 个 backup 节点。
  • 分片集群中 mongos 接入层至少 2 个实例（min_members=2），避免单点。

2.4类型二：MongoShardedCluster（分片集群）类型

由 3 类角色 协同工作：

mongos #1路由 / 接入层
mongos #2路由 / 接入层
▼
config server (RS)元数据 / chunk 路由
▼
Shard 1 (RS)数据分片 1
Shard 2 (RS)数据分片 2
Shard N (RS)数据分片 N
  • 常量：MongoShardedCluster
  • 每个 shard 通常本身就是一个 副本集，配合 config server 提供高可用 + 横向扩展。
  • 适用：单集群容量 / 写入需多分片线性扩展时。
⚠
选型不确定时的建议

优先选 副本集；确需水平分片再迁分片集群。详见 §3.3 选型决策。
